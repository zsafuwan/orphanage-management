# Database-backed care forms

The application uses the existing PostgreSQL `postgres` database. No migrations or table creation are needed or performed for this integration.

Use the project's existing child, staff, and director pages and forms. There is no separate record-management page. Foreign-key dropdowns show saved records; primary IDs are generated by PostgreSQL. Organizations, orphanages, and subjects use the existing database tables; no new management screen is added for them.

The existing child admission, medical, examination-results, and appointment dialogs also save to PostgreSQL. Admission can create an optional baseline Medical_Record in the same transaction as the child. Examination results create Education_Record, reuse or create Subject rows, and create Subject_Result rows in one transaction. Director health notes save to Welfare_FollowUp. Director overall-score changes update the latest Education_Record.

Child photos are optional JPG, PNG or WebP uploads up to 5 MB and 8000 pixels per side. Files are stored privately under `storage/app/private/child-photos`; only the relative path is saved in `Child.Child_Photo_Path`. Existing admission forms upload photos, and existing child cards offer Change photo. Images are served through the same local-only access middleware as care records, with no public storage link. Enable the nullable column on an existing database with `php artisan care:enable-child-photos`; this command creates no tables. Unsupported fields (school name, blood type, allergies, and other details without matching columns) remain disabled. Attendance is an integer number of days, while overall and subject results are percentages between 0 and 100. Browser-local child demo records are not imported automatically.

Volunteer, staff, donation, inventory, duty, and welfare-request tools remain explicitly labelled browser-only demos because there are no matching database tables. The public volunteer page also explains that its data remains in the browser.

The current portal has simulated roles rather than real staff authentication. The CareAccess middleware therefore limits the new database read/write routes to local-environment requests from loopback addresses. Role switching in the UI does not grant remote database access.

## Verification

The opt-in PostgreSQL feature tests operate on existing tables inside rollback transactions. They never migrate, truncate, or create tables. PostgreSQL identity sequences can advance during rolled-back tests, which is normal.

```powershell
$env:CARE_DATABASE_TESTS='1'
php vendor/bin/phpunit tests/Feature/CareRecordsTest.php tests/Feature/PortalDesignTest.php
node --test tests/js/database.test.cjs
```

Do not run `migrate:fresh` against this database.
